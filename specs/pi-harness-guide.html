Purpose

Build a single self-contained standalone HTML field guide — “Pi — The Coding Harness” — for an engineer who does not yet have Pi installed and wants to go from zero to a well-configured, extended, editor-integrated setup. The guide covers, in reading order: what Pi is (earendil-works/pi — unified LLM API, agent loop, TUI, coding-agent CLI; v0.84.3, MIT, ~98K stars), a Quickstart (install → auth → first session), a Recommended Setup (Node ≥ 22.19.0, terminal + tmux csi-u, settings, AGENTS.md, trust model, a starter package stack), an Advanced Setup (writing TypeScript extensions against ExtensionAPI, authoring/publishing packages, custom providers, SDK/RPC modes, containerization), a VS Code / Cursor section so extension TypeScript resolves cleanly in the editor, a curated tour of 12 ecosystem packages, and a dedicated section on IndyDevDan (disler)’s Pi work — grounded in the local clones under ~/dev/disler-aka-indydevdan/. Every claim carries a deep link to pi.dev/docs, the GitHub repo, or a disler repo file. The finished doc is imported into oh-my-html-docs, validated end-to-end with playwright-cli, committed conventionally, and shipped as a PR.

Problem

Pi’s docs are excellent but distributed: install lives in Quickstart, the tmux csi-u fix on its own page, the trust model under Security, MCP support isn’t in core at all (it arrives via the pi-mcp-adapter package — the registry’s #1 at 628K downloads/month), and the extension API is documented separately from the editor setup needed to write one comfortably. A newcomer must also discover non-obvious facts the hard way: Pi needs Node ≥ 22.19.0 (a legacy-node20 dist-tag exists at 0.74.2); npm install -g wants --ignore-scripts; Pi does not auto-load .env — keys must be exported before launch; Gemini reads GEMINI_API_KEY, not GOOGLE_GENERATIVE_AI_API_KEY; and project-local extensions only load after an explicit /trust. Meanwhile the best working examples of “Pi as a programmable platform” — 18 extensions in pi-vs-claude-code, a full observability stack, a multi-model fusion harness, a builder/verifier two-agent system — live scattered across IndyDevDan’s repos with no single map. There is no one page that takes an engineer from “never installed it” to “extended it, in my editor, with the ecosystem’s best packages.”

Solution

Author a new standalone bundle in a Pi-synced identity — the “engineer’s notebook”: paper #F4F2ED with a graph-paper grid, ink #1C222B, steel-blue accent (#3D6E9E, derived from pi.dev’s #6a9fcc), rust #8F3222 secondary, serif-italic display + mono labels — echoing pi.dev itself rather than the house dark family. Structure it as a progressive setup ladder: Quickstart → Recommended → Advanced, each rung ending in a verifiable state. Reuse the proven interaction skeleton from the sibling guides (sticky TOC + scroll-spy, copy-button command blocks, print CSS) re-skinned to paper. Ground everything research-first: commit the harvested pi.dev/docs facts and the disler repo survey into specs/pi-harness-guide/research/ before writing a glyph — no claim without a source link. Diagrams ship as inline SVG in the guide (self-contained, no image requests); generated PNGs are used only for this plan and the card preview. Then import via scripts/new_doc.py, validate with the repo’s playwright-cli recipe, and open a conventional-commit PR.

Design decisions & rejected alternatives

  • Setup-ladder structure over reference structure. The user is a from-zero reader; each rung ends in a verifiable state (“pi runs” → “pi is comfortable” → “pi is yours”). The reference material (commands, keybindings, events) is embedded in the rung where it becomes relevant, then aggregated in §11/§12.
  • Rejected: a Claude Code comparison as the guide’s spine. The sibling guides own the conversion-table genre; this guide is a setup guide. The comparison appears once, short, attributed to disler (§09).
  • Rejected: reproducing disler code wholesale. His repos are MIT but the guide quotes ≤20-line snippets with repo/path/video attribution and links out — the section is a map to his work, not a mirror of it.
  • Research is committed, not scratch — same provenance discipline as the codex/copilot guides; volatile numbers (stars, downloads, versions) are dated in prose.
  • Plan images degrade gracefully. The image scripts need OPENAI_API_KEY (loaded from a cwd .env, which tooling here can’t inspect). Generation is attempted; on failure the <figure> placeholders remain as comments — exactly how the codex and copilot plan docs shipped — and the guide itself never depends on generated images (Q4).
  • Dependencies: none added to this repo. The guide is self-contained HTML + Google Fonts links, matching every sibling.
