Purpose

Build a single self-contained standalone HTML field guide — “Copilot CLI vs Claude Code” — that lets an engineer fluent in one terminal agent become instantly productive in the other. The guide is organized around conversion tables: config & context files (CLAUDE.md ↔ AGENTS.md), CLI flags, slash commands, customization surfaces (hooks / skills / subagents / MCP / plugins), the permission & safety models, and headless / CI / GitHub Actions usage — closing with an honest accounting of what each tool has that the other doesn’t. Every factual claim is grounded in doc pages harvested via curl pipelines that also ship as reusable justfile recipes. The finished doc is imported into oh-my-html-docs via just add and validated end-to-end with playwright-cli.

Problem

Copilot CLI and Claude Code have converged on the same shape — interactive TUI with a plan mode, headless -p mode, MCP, skills, subagents, hooks, plugins — but every concept wears a different name, lives in a different file, and takes a different flag. An engineer switching between them (or evaluating one from the other) has to stitch the answer together from two separately-organized doc sites: GitHub Docs buries Copilot CLI across concepts / how-tos / reference trees, and Claude Code’s docs mirror none of that structure. There is no conversion table anywhere that answers the practical questions — where is CLAUDE.md in Copilot? what is --dangerously-skip-permissions called? which hook events exist on both sides? — and vendor comparisons that do exist are marketing, not engineering: they never state what the other tool does better.

Solution

Author a new standalone bundle in the house dark identity (Copilot purple #A371F7 accent on the shared #0A0C10 surface family) with the repo’s signature components: three .matrix verdict tables with the Copilot column tinted (the subject under examination), plain conversion tables ordered Concept | Claude Code | Copilot CLI | Notes, flip-card “switching gotchas,” terminal-chrome code blocks, and a copy-button cheat sheet of equivalent command pairs. Research first: harvest ~12–18 doc pages into a committed research/ directory using two verified curl pipelines (GitHub Docs’ search + article-body API; Claude Code’s .md-suffix raw markdown + llms.txt index), promote the pipelines to just ghdocs / ghdoc / ccdocs / ccdoc recipes, and resolve every uncertain mapping before a single glyph is committed — no .n (“doesn’t have it”) claim without a citation. Then import via just add and validate with the repo’s playwright-cli recipe.

[x] Phase 1: Justfile Doc-Search Recipes

Promote the two verified curl pipelines into four reusable just recipes so doc lookups are one command during research — and forever after. The justfile’s recipe shell is zsh; all query encoding goes through curl -G --data-urlencode so multi-word queries survive quoting, and -f makes the unofficial endpoints fail loudly.

1.1 Add the recipes

  • [x] just ghdocs QUERY — GitHub Docs search: curl -fsG "https://docs.github.com/api/search/v1" --data-urlencode "query=QUERY" --data-urlencode "version=free-pro-team@latest" --data-urlencode "language=en" --data-urlencode "size=10" --data-urlencode "client_name=oh-my-html-docs" piped through jq -r '.hits[] | "\(.url) — \(.title)"'.
  • [x] just ghdoc PATHNAME — full article as markdown: curl -fsG "https://docs.github.com/api/article/body" --data-urlencode "pathname=PATHNAME".

Questionables

Open questions, phrased yes/no where possible. Each carries the assumption the build proceeds on unless you say otherwise.

Q1 — Accept that the GitHub Docs API (/api/search/v1, /api/article/body) is unofficial and may break? (yes/no)

Assumption: yes. Both endpoints are internal to docs.github.com with no stability contract. Mitigation: recipes use curl -f so failures are loud, and all research snapshots are committed under research/, so authoring and future edits never depend on the live endpoints.

Q2 — Is “As of July 2026” + a dated provenance section enough to handle Copilot CLI churn? (yes/no)

Assumption: yes. Copilot CLI is in public preview and moves fast. The hero badge, §12 provenance, and a note telling future editors to re-run just ghdoc on the cited pathnames make staleness detectable and repairable rather than invisible.

Q3 — Enforce “no .n without a citation; uncertain → .p” even where it makes the matrices look less decisive? (yes/no)

Assumption: yes. Every “tool X lacks feature Y” cell is a falsifiable claim with reputational cost. A .p with a footnote is honest; a wrong .n is the one error class this doc can’t afford.

Q4 — Ship v1 with zero embedded images (placeholders as HTML comments)? (yes/no)

Assumption: yes — per the user’s explicit decision. The doc is table-first; images add load weight and generation cost without carrying the conversion content. Slots exist in the markup, so a later image pass is a pure addition.

Q5 — Call scripts/new_doc.py directly (not just add) for the import? (yes/no)

Assumption: yes. The opus-5 build recorded that the just add recipe drops quoting on multi-word titles. Direct uv run scripts/new_doc.py … with quoted flags is the reliable path; fixing the recipe’s quoting is out of scope (worth a follow-up).

Q6 — Treat just links (lychee) as advisory rather than a gate for this doc? (yes/no)

Assumption: yes. §12 adds many docs.github.com / code.claude.com links; lychee may rate-limit or transiently fail on them. Run it, read the output, but don’t block completion on it.

Q7 — Keep pricing/plan comparison to one callout (no dedicated pricing section)? (yes/no)

Assumption: yes. Pricing churns faster than features and both vendors gate models by plan tier; a §01 callout naming the models-per-subscription difference conveys the strategic point without a table that would be stale in a quarter.

Design decisions & rejected alternatives

  • Copilot column tinted in every matrix. The reader baseline is a Claude Code user examining Copilot; the tinted column marks the subject under examination, mirroring how the cmux/opus-5 guides tint “our thing.”
  • Rejected: dual accents (coral vs purple). The house rule is ONE accent per doc; two accents would fight the verdict glyph colors. Purple carries the doc; Claude-side identity is carried by column order and labels.
  • Rejected: specs/guides/ staging. That directory doesn’t exist — the real convention is the plan-name sibling dir, so staging lives at specs/copilot-cli-vs-claude-code/doc/ with exactly one .html.
  • Research is committed, not scratch. Claims in a comparison doc need auditable provenance; research/ under the plan’s sibling dir mirrors the images-dir convention and survives the session.
  • Dependencies: none added. jq is used by just ghdocs (present on this machine); the guide itself stays dependency-free self-contained HTML (Google Fonts links only, matching both existing guides).
